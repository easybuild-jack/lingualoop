# Supabase 业务代码复查报告

对照 `docs/supabase-dev-plan.md`（第 5 节）和已定稿的 `supabase/schema.sql`（方案 B），复查分支 `cursor/supabase-review-report-1238` 上相对 `dev2` 的全部业务代码改动。

## 总体结论

主体实现与开发计划、脚本一致，8 个流程的主路径都能跑通。

1. 纯本地模式不受影响。
2. 注册、登录、改密码、退出登录工作正常。
3. 进度按 `account_id` 隔离，内容按"NULL 为共享、非空为个人"区分可见范围。
4. 官方词库进度可以入库和迁移。
5. H1–H6 修复已生效。
6. 与脚本的函数、字段、约束一致。

复查发现 **2 个高、2 个中、1 个低** 的明确 bug，范围小，修复不改变已定规则，本轮已一并修掉并补了测试。

- **高（已修）**：云模式下 `getCustomBooks` 会用固定 id 的示例词库覆盖别的账号上传的个人示例词库，造成数据丢失。
- **高（已修）**：账号变化后页面还没重载（典型场景：另一个标签页切换了账号）时，上一个账号内存里的进度会写进新账号。本机缓存和云端都会被写入，正是"切换账号不串进度"要防的情况。
- **中（已修）**：云模式下"旧测试数据清理"会删掉别的账号的共享词库，并连带清掉所有账号在该库上的进度。
- **中（已修）**：退出登录前没有等待待推送的进度，最后约 1 秒内的学习位置变更会丢失。
- **低（已修）**：收词时如果"并入收藏词库"失败，收件箱行仍会被标为完成，词已加星但不在收藏词库里。

另有 3 个中、若干低的问题，涉及产品行为或需要改脚本，本轮没有动，列在第二节，等作者确认。

**没有修改数据库脚本。** 本轮业务代码改动只限下面列出的文件。

## 二、待作者确认的问题（本轮未修改）

> 作者已逐条确认，处理结果见第六节。

### 中

1. **改单词时整本覆盖 `words`，并会改动共享词库。**
   - 位置：`src/db/index.ts` 第 802–826 行，`saveWordOverride`。
   - 现状：云模式下先读出当前账号可见的全部自定义词库，再把含该词的词库整个 `words` 数组 `update` 回去。
   - 后果 1：这是读改写。另一台设备或收件箱同时往同一本书并词（`merge_words_into_book`）时，后写的一方会抹掉先写的新词，属于 H4 的残留。
   - 后果 2：`word_overrides` 按账号保存，但这里会把 A 的修改写进共享词库，B 看到的词条也跟着变。
   - 建议：二选一，取决于"word_overrides 是否共享"这个待定项。(a) 只改个人词库，共享词库不动，界面读取时再套用本账号的覆盖；(b) 新增一个"在库内原位修改单个词"的数据库函数（需要改脚本）。
2. **23514 被静默吞掉。**
   - 位置：`src/db/index.ts` 第 184、543、598、690、835 行的 `catch` 只打印日志。
   - 现状：开发计划 5.3 要求遇到 23514（单元已属于别的书、进度不能改挂）时"重新加载当前词库，不要静默吞掉"。目前练习照常进行，但这一词的进度没有保存，用户无感知。
   - 触发场景：同一个 `unit_id` 已挂在另一本书下。理论上只在官方单元目录调整、或自定义词库 id 冲突时出现。
   - 建议：在 `useWorkspaceStore` 里识别 `CloudRequestError.code === '23514'`，提示并重新加载当前词库。这会改交互，需要作者确认。
3. **固定 id 内容的迁移会被静默跳过，进度却照常上传。**
   - 位置：`src/core/cloud/migrate.ts` 第 90 行。
   - 现状：上传走"只补插不覆盖"。如果云端已有同 id 的行（最常见的是 `book_custom_sample`，以及旧版固定 id 的 `book_custom_collected`），本机这本书会被跳过，只计入 `skipped`。如果对方是别的账号的个人词库，当前账号还看不到它。
   - 后果：用户在本地往示例词库里导入过的词不会上传；这些词的单元进度却会上传，指向一本空的或看不到的书。
   - 补充：开发计划 5.5 写的是"示例词库作为共享内容"，但上传时选"个人"会把示例词库存成个人。
   - 建议（需作者定）：(a) 上传时示例词库始终存为共享，并把本地示例词库里的词通过 `merge_words_into_book` 并进去；(b) 本地示例词库有用户词时，换成新的 `book_custom_<时间戳>` id 并改写相关进度。

### 低

4. **书内位置会推送默认的 0。**
   - 位置：`src/core/cloud/sync.ts` 第 163 行。
   - 现状：水合合并时，每本书缺的模式会补成 0，随后被当作"变化"推送。
   - 影响：多出一些 `unit_index = 0` 的行。极端情况下，另一台设备刚写入的真实位置会被这次推送（`updated_at` 取本机当前时间）覆盖。
   - 建议：合并时只保留真实存在的模式（需要把 `BookModeUnitRecord` 改为部分字段），或者推送时跳过值为 0 且云端没有的条目。
5. **`app_state` 整行"后写者胜"。**
   - 现状：学习位置、循环次数、已学词根整行 upsert，脚本没有对 `app_state` 挂 `tg_newer_wins`。两台设备交替使用时，晚推送的一方会覆盖对方。
   - 说明：开发计划把"循环次数归属"列为待定项，按要求没有大改。
6. **关闭页面前的推送不保证送达。**
   - 位置：`sync.ts` 第 350 行。
   - 现状：`pagehide` / `visibilitychange` 时会立即推送，但普通 fetch 会随页面卸载被取消。关页前约 1.2 秒内的位置变更可能丢失。
   - 建议：给 supabase 客户端的 fetch 加 `keepalive: true`，或缩短防抖时间。
7. **"未配置 AI Key"的收件箱行会被耗尽重试次数。**
   - 位置：`collector.ts` 第 114 行。
   - 现状：这类失败按"可重试"处理，但每 20 秒一轮。未配置 Key 时，大约 5 轮后就进入 failed 终态，之后配置了 Key 也不会再处理。
   - 建议：没有 AI Key 时不认领需要查词的行，或者不计入重试次数。这属于产品选择。
8. **守卫进入错误状态后的行为。**
   - 位置：`CloudSyncGate.tsx` 第 80–107 行。
   - 现状：体检或水合失败时，不会启动进度推送，但计数、单元进度等直读直写仍会尝试访问云端。错误期间改动的学习位置不会推送，点"重试"后以云端为准。另外，`offline` 事件只弹提示，不停止推送；推送失败后每 5 秒重试一次。
   - 建议：维持现状并在说明中写清；或在错误状态下把学习位置标记为待推送，重试成功后补推。
9. **永久性错误会无限重试。**
   - 现状：推送失败后每 5 秒重试，不区分错误类型。对 23503（账号已被删除）、23514 这类重试也不会成功的错误，会一直刷请求。
   - 建议：只对网络类错误重试。
10. **共享内容"后写者胜"，可能复活已删除内容。**
    - 位置：`sync.ts` 第 297–308 行的翻译句库推送，以及阅读文章、视频的 `putArticle` / `putItem`。
    - 现状：都按 id 整行 upsert。两个账号同时改同一个共享句库时后写者胜。A 删除共享句库后，B 的页面里还有它；B 再编辑这本句库时，upsert 会把它重新建出来。
    - 建议：已有行只用带可见范围的 `update`，只有新建时才 insert。
11. **词库页没有共享/个人标记，删除共享词库也没有额外提示。**
    - 现状：删除共享词库会让所有账号失去它和对应进度（这是已定规则），确认框里没有说明。
    - 建议：在词库卡片上加"共享 / 个人"标签，删除共享词库时在确认文案里写明影响。
12. **视频时长不入库。**
    - 位置：`RadioUploadModal.tsx` 第 141 行，`radio/page.tsx` 第 302 行。
    - 现状：链接视频入库时 `duration` 固定为 60，播放时读到的真实时长只更新页面内存，不写回数据库。播放次数也只在内存里。
    - 建议：入库时写 0，首次读到真实时长后 `putItem` 一次。
13. **`reconcileUnitProgressRecord` 在云模式下仍是读改写。**
    - 位置：`src/db/index.ts` 第 499 行起。
    - 现状：只在词库内容变化后修剪进度时调用。已改为"内容没变就不写"，残余竞态很小，暂不处理。

## 四、测试说明

### 环境
- 本机 PostgreSQL 16 新建测试库，执行 `supabase/schema.sql`。

### 7.5 需要作者确认

1. **AI 补全只写当前正在学的那本自定义词库**：同一个词出现在多本自定义词库里时，其他词库不会跟着改（数据库模式下逐本读出全部词库代价太大）。补全的词不在当前词库里时（例如在错词本里补全别的词库的词）不写词库，只进本机 AI 缓存。
2. **错词标记的合并**：按「最后练习时间更晚的一方为准」，所以本地较旧的错词标记不会把数据库里已消除的错词重新标回去，反过来也一样。如果希望错词标记也「只增不减」（任一方是错词就算错词），改 `mergeWordRecord` 一行即可。
3. **同步资料里阅读文章按整篇更新**：数据库里已有的文章会被本地内容整篇覆盖（段落没有 id，没法逐段合并）。
4. **同步进度和练习同时进行**：同步是先读后写，同步过程中如果另一台设备正在练习同一个词，那一次计数可能被覆盖。这是手动操作，影响很小。
5. **写入失败后**：失败那次不重发，但下一次学习位置变化时会把当时与数据库不同的字段一起写入，也就是"下一次正常写入会带上上次没写进去的位置"。如果希望失败后不再写，需要改回停止写入。

### 8.1 AI 补全（7.5 第 1 条）：确认现有实现符合

`applyAiFillToCustomBook` 只写当前词库（`currentBook`），词不在当前词库里就返回、只进本机 AI 缓存。是否写本地由当时的模式决定（`getRepositories().mode`），数据库模式下别人的个人词库不写，官方词库不写。没有改动。

### 8.2 同步进度里单词记录的合并（7.5 第 2 条）

不再比较最后练习时间，各字段都按「只增不减」处理（`mergeWordRecord`，`src/core/cloud/manualSync.ts`）：

| 字段 | 规则 |
|---|---|
| 错词标记 | 任一方是错词就是错词；本地或数据库没有标记，同步后都会加上，永远不会因为同步被去掉 |
| 生词标记、已掌握 | 任一方为真即为真 |
| 累计练习次数、默写错误次数 | 取较大值 |
| 最后练习时间 | 取较晚的 |
| 连续答对次数 | 合并后是错词时，只取标记为错词那一方的次数（两方都是错词取较大值）；合并后不是错词时取较大值 |

连续答对次数是「移出错词本」的进度：默写连对 3 次自动移出。如果直接取两边较大值，已经移出错词本那一方留下的连对次数（≥ 3）会带进来，重新加上的错词答对一次就会被移出，错词标记等于没加。所以它跟着错词标记走，只取错词那一方的次数。这是唯一可能让数据库里某个数变小的情况：数据库那边原本不是错词、因本地是错词而被加上时，连对次数换成本地错词那一方的。

### 8.3 写入失败、数据库无法访问时自动切到本地模式（7.5 第 4 条）

新增 `src/core/cloud/fallback.ts`。下列情况在已登录的云模式下自动切到本地模式，页面重载后在顶部提示「数据库暂时无法访问，已切换到本地模式，数据库恢复后请到设置里手动同步资料和进度。」，括号里附上原因。这条提示要用户手动关闭：

- 任何写入数据库失败：学习进度、单词记录、单元进度、词库、导入、AI 补全写回、句库、文章、视频；
- 连不上数据库，读写都算：启动体检失败、启动载入进度失败、浏览器断网、收件箱轮询连不上；
- 其他读取失败（例如约束或权限报错）只在顶部提示，不切换。

切换时：
- 只设置「临时用本地模式」标记，与手动点这个入口完全相同，不回传、不重试，也不覆盖、不清空任何数据；
- 失败后本页立即停止写数据库，上一轮「之后的变化把差异字段一起写入」的行为已经去掉；
- 重载后读写都走本机。本机那份是上次本地模式留下的数据，可能比数据库旧，甚至为空，用户在此基础上继续学习；
- 数据库恢复后，用户在设置里点「恢复云端连接」，页面从数据库重新载入，再手动点「同步资料」「同步进度」，按第七节的加法规则合并。设置面板在本地模式下会提示这一步；
- 未登录时的失败（例如跳转登录页前页面发出的请求）不触发切换；
- 设置里手动同步本身失败时只在面板里显示原因，不切换，因为用户正在主动操作。
